# Rollup queries: SurrealDB vs PostgreSQL vs SQLite

2026-11-04. Script: `bench/bench.py` (raw numbers: `bench/results.json`, log: `bench/run.log`).
Re-run with `python3 -I bench/bench.py [orders ...]`.

## Why

The ERP's pages show per-row totals computed from child rows: an order's net value and item
count, whether it has been invoiced, how much of an invoice is still unpaid. In SurrealDB these
were `expr:` columns written the way the Vantage skills show:

```sql
math::sum((SELECT VALUE amount FROM sales_order_line WHERE sales_order = $parent.id))
```

Pages took seconds to load, and writes queued behind those reads (a payment run's saves took up
to 18 s, with audit-log timeouts). This benchmark checks whether that is SurrealDB itself and how
the fix compares with relational databases.

## Setup

- Same synthetic data in every engine, generated by the script (seeded, so repeatable):
  orders with 1–4 lines, ~80% invoiced, ~85% of invoices paid. Indexes on every foreign key and on
  `order_date`, in every engine.
- **surreal-parent**: SurrealDB 3.2.4 (RocksDB, the project's Docker container), correlated
  subqueries on `$parent.id` as above.
- **surreal-refs**: the same SurrealDB, link fields declared `REFERENCE`, rollups written
  `math::sum(<~line.amount)` and `count(<~invoice[WHERE status != 'void'])`. This is what the app
  uses now.
- **postgres**: PostgreSQL 17 (Docker, data on tmpfs), plain SQL correlated subqueries.
- **sqlite**: SQLite 3.53 in-process from Python, same SQL.
- Before timing, the script checks that all four return the same number of rows for every query.
- Timing is each engine's own: SurrealDB's per-statement `time` (no HTTP), psql `\timing`,
  SQLite measured around `execute().fetchall()` in-process. One warm-up, then the median of 5
  runs. `*` = a single run (the warm-up alone took over 8 s). `—` = not run: it would have taken
  many minutes per query.
- Machine: the developer's Mac, Docker via Colima. Absolute numbers are machine-specific; the ratios
  are the point.

## Queries

| Query | What a page does with it |
|---|---|
| `page_40_by_date` | First 40 sales orders, newest first, with total, item count, invoiced flag |
| `all_orders_with_totals` | The same for every order (what loading a whole collection does) |
| `page_40_by_total` | First 40 orders by net value: every total must be computed to sort |
| `overdue_invoices` | Issued, past due, amount > sum of its payments |
| `lines_of_one_order` | One order's lines through the foreign-key index (baseline) |

## What it shows

1. **The `$parent` subquery pattern is quadratic in SurrealDB 3.2.** The index on the foreign key
   is used for a literal (`lines_of_one_order`: 0.2 ms) but not when the value comes from
   `$parent` (`EXPLAIN FULL`: table scan, "pre_decode_filter: no (unsupported predicate)"). Each
   order scans every line: 4× the data costs ~16× the time (4.1 s → 67 s for all totals). Even a
   40-row page grows with the table (166 ms → 1.5 s), because each of the 40 rows scans all lines.
2. **Record references fix the shape, not the constant.** `<~line` follows the stored reference
   directly: growth becomes linear (15.6 → 63.2 → 151.3 ms for all totals) and a 40-row page stays
   flat at ~2 ms. That is 260× to over 1,000× faster than the `$parent` form at these sizes.
3. **PostgreSQL and SQLite are still 5–15× faster than SurrealDB with references** on the same
   rollups (e.g. all totals at 10,000 orders: 151 ms vs 28 ms vs 11 ms), and they get there with
   the plain correlated subquery: their planners use the foreign-key index for it. SQLite's lead is
   partly being in-process (no client protocol at all).
4. For this app's real size (~800 orders) all three are fast enough once SurrealDB uses
   references: ~0.1 s for a page including the HTTP round-trip.

## Consequences for this project

- Every parent→child rollup in `table/*.yaml` uses `<~child` (references declared in
  `tests/schema.surql`). References are recorded only on write: declare them before loading data.
- Filters on a derived value that would need a per-row sum (overdue invoices) use a stored running
  total kept by a database event (`paid_amount`), since payments are immutable.
- If the data grows by orders of magnitude, or most work becomes reporting, PostgreSQL is the
  stronger backend for this workload; the Vantage tables and pages would carry over, with the
  `expr:` rollups becoming query tables (`expr:` is SurrealDB-only).
